# Calorie Agent 交流体验与上下文治理规格

状态：2026-11-03 上下文治理方向已采用，待实现。回复和业务规则继续有效；本轮交付实现与隔离候选验收，正式发布按部署任务执行。

个人业务见 [个人功能规格](PERSONAL_CALORIE_SPEC.md)，需求见 [REQUIREMENTS.md](REQUIREMENTS.md)，实际接口见 [contracts/](contracts/)。本规格管理发给模型的信息及话题记忆；[COS 规格](LATENCY_OPTIMIZATION_SPEC.md) 管理持久化、物理保留和回收。上下文投影不能删除账本、待办、执行事实或防重凭据。

## 1. 目标与范围

用户记账少等待，旧话题可接续；摘要不替代当前事实，不改变补全、确认和恢复结果。

| 项目 | 决定 |
|---|---|
| 本轮范围 | 摘要失败覆盖、完整请求计量、动态状态视图、历史查询分级返回、知识证据去重、有预算约束的后台摘要及相应验收。 |
| 沿用 | DeepSeek 型号及思考模式、create_agent 原生循环、现有八工具、COS＋飞书、三种预设、飞书／CLI／DSH 入口及会话隔离。 |
| 话题连续性 | 近期完整轮次的清洁表示＋有界后台摘要。背景摘要只处理已完成对话，不进入当前请求等待链路。 |
| 业务事实 | 数值、对象、日期、已执行状态由对应工具事实提供；生效设置、有效提案和未完事项使用结构化状态。 |
| 性能 | 普通已知食物记餐、改量及今日查询暖样本各 ≤5秒，ACK ≤3秒；主模型轮数不能因删去必要上下文而增加。冷启动、后台摘要耗时和费用单列。 |
| 不扩展 | 不换模型或框架，不新增记忆数据库、向量检索、记忆工具、专用常驻服务或自动用户画像，不实施 COS 清理。 |

优先复用现有 model_view、history_messages、标准消息序列化和 LangChain 消息裁剪原语。移除前台同步摘要及错误文本替换历史的路径，不以升级整套依赖作为修复前提。

## 2. 回复与确认行为

| 用户意图 | 预期行为 |
|---|---|
| 明确记录／复用 | 简短确认＋本餐热量，估算时说明；明细按需展开。 |
| 补全／改量／撤销 | 沿用原餐、原日期和已知条件，说明变化及原餐当前有效合计。 |
| 今日或历史合计 | 直接回答所问范围和指标，不重复完整账本。 |
| 知识问题 | 先回答，再给有用依据和实际来源；证据不足时给一般解释，简短说明具体缺口。 |
| 缺项或真实歧义 | 可确定项先处理，合并询问影响结果的剩余条件。 |
| 闲聊或换话题 | 自然接续，保留独立未完事项。 |
| 主动写入建议 | 先交付固定动作和参数的提案；紧邻有效确认后才执行。 |

模型自然组织正文。工具负责来源换算、计算、读写和防重；用户提供的名字、日期、数量、候选编号及项数可正常复述。餐次缺省沿用 unknown。

回执范围保持一致：新增／复用为目标餐，补全为原餐所有有效项，改量／撤销为受影响原餐更新后的合计；多餐分别按 meal_id 汇总。record_meal.data.total 表示本次完成批次，meal_totals 表示原餐，query_today.data.total 表示全天，calculate_meal.data.total 表示方案，不能混用。

提案保留 proposal_id、固定动作／目标／参数、目标版本、回复关联及 presented；交付成功才设 presented。换话题、取消或参数修订按既有规则处理。摘要中的“曾经同意”不构成本次确认，旧回复重投不能恢复已失效提案。

正常回复不触发模板兜底。异常回执只使用当前请求已确认的最终事实，分别说明完成与未完成部分；发送恢复复用已存正文和 UUID。保留 model_reply、reply、response_adjustments、reply_source 及实际检查范围。

## 3. 完整请求预算

### 3.1 计量与默认值

每次模型 HTTP 请求组装完成后检查实际发送内容，包含 system、最终 tools schema、动态状态、摘要、历史消息、当前用户输入、原生工具调用参数／结果、供应商要求回传的 reasoning_content 及协议开销。主调用和后台摘要都必须经过该检查；同一字段不重复计量。

首版工程默认值：

| 项目 | 值 |
|---|---|
| 主请求输入目标 | 16,000 tokens，属于性能目标，不是拒绝合理请求的阈值。 |
| 主请求输出预留／max_tokens | 8,192 tokens，包含该服务计入输出的思考与正文；保持现有思考模式。 |
| 协议余量 | 2,048 tokens。硬输入上限＝当前服务模型窗口 C－输出预留－余量。 |
| 近期保留 | 至少最近2个已完成用户轮次的清洁表示，加当前完整轮次；有效提案／待办引用另行保留。 |
| 后台触发 | 保留近期2轮后，尚未摘要的已完成前缀达到4,000 tokens。 |
| 摘要输入／输出 | 输入目标12,000 tokens；正文最多1,024 tokens；摘要请求 max_tokens 为4,096，另预留协议余量。 |

实现时绑定当前部署服务及模型的窗口 C、匹配的本地 tokenizer／消息编码版本，并在交付记录列出实际值与依据。只打包必要编码资源，不加载模型权重或联网计数；不能用知识索引 tokenizer 代替 DeepSeek 计量。依据见 [DeepSeek token 计量](https://api-docs.deepseek.com/quick_start/token_usage/)。

本地计量与服务端 usage 分开记录，用候选请求核对差额；协议余量不得被当作额外输入额度。max_tokens 必须实际进入 HTTP body；finish_reason 表明截断时，不得把残缺调用参数或正文认作完整成功。

旧 summary_trigger_tokens／summary_keep_tokens 的前台触发语义被本节取代，配置及消费者一起更新；不保留两套同时生效的策略。

### 3.2 输入选择与超限

按以下顺序构造每次请求：

1. 固定系统规则和八工具定义，保持顺序稳定，不新增模型选择器。
2. 当前原始用户消息、当前工具交换及最新结构化状态视图。
3. 最近2个已完成轮次的清洁表示、有效摘要，再按预算加入较新的未覆盖历史。

动态视图每次模型调用重建，不复用本轮开始时的状态；视图不追加到会话原文或摘要来源。持久清洁对话来源、执行审计和本次请求投影分开保存：预算裁剪不得写回来源、推进摘要覆盖游标或覆盖恢复所需原生消息。普通正文更新不能把完整审计再次塞回模型。

历史业务回执不作为当前事实注入；工具历史仅保留明确标记 historical 的定位信息，知识历史按需要保留证据和对话背景。当前调用／结果配对、固定 call_id、原用户消息及协议必需的 reasoning 必须保留。移除历史按完整轮次／调用组进行，不截 JSON、不留下孤立 ToolMessage；旧格式缺失的当前轮从原收件及已存调用恢复。

超过16,000目标时，先去重证据并移出已由摘要覆盖、或不属于近期2轮的旧轮次；未覆盖的原文继续保存并等待后台处理。仍超目标但未达硬上限时，允许必要输入并记录原因，不为达标删除有效条件。

超过硬上限时，本次不发送该模型请求、不重新调用同一超额请求。预算超限作为不可自动重试的已确定终态处理：保留已提交事实，终结本次未执行计划，交付事实回执及缩小输入／范围的具体要求后推进收件游标；不进入阻塞后续消息的 needs_attention。独立未完事项继续保留，新消息可以接续；旧收件重投只返回原回执，不恢复被终止动作。若此前写入结果未知，先按既有提交恢复规则处理，不能借预算超限判定该写入失败。

## 4. 状态与工具视图

### 4.1 结构化状态

| 状态 | 本次模型视图 | 持久语义 |
|---|---|---|
| 设置 | 长期偏好、常用餐名称、有效提醒及与原业务日期相关的目标配置；不注入全部历史 daily_targets／份量库 | 完整设置保留，数值回答仍由对应工具取当前生效事实。 |
| refs／最近餐 | 最近餐及近期实际可操作引用的 ID、名称、日期／餐次，不重复注入全量 refs | 原身份校验集合保留，历史餐通过 query_history 的 items 模式重新定位。 |
| unfinished | 所有仍有效待办的 ID、原日期／食物、缺项、已知数量及选择所需的候选编号／区分信息 | 完整候选、offered_message_id、prepared.pending_before 等仍由后台校验；不因变旧或换话题删除。 |
| proposal | 当前有效提案的动作、对象、参数和展示状态 | 固定身份、版本与交付绑定继续生效，不能从摘要推定。 |
| 当前工具事实 | 当前决策需要的结果、缺项和来源 | 完整结果、prepared、执行审计和防重记录不被模型视图替换。 |

完成、取消或失效的待办／提案立即退出模型视图。未完项没有独立读工具，本轮不能隐藏其不可重新发现的 ID 或候选绑定；超大必要状态走第3节硬上限处理，不增加第九个工具。

记忆只提供过去的意图和话题背景。当前用户修订、当前有效设置及工具事实优先；记忆不能自动写设置、授权动作或声称某次业务已完成。

### 4.2 查询结果

保留 query_today 的 calories／summary／items。query_history 在原工具内增加 detail：

| detail | 用途及模型可见结果 |
|---|---|
| summary（默认） | 日期范围、count、准确 total；合计问题不携带逐项 items。 |
| daily | 日期范围、count、total 及按日 count／total；无记录日标记未记录，不推断用户没有进食。 |
| items | 匹配范围内完整餐项定位信息与所需营养；用于历史改量、复用及明细请求。 |

三种详情使用同一筛选集合与营养计算，范围端点语义不变。完整持久结果保存实际读取事实，模型投影按 detail 取舍；同步调整依赖 data.items 的模型提示、历史引用提取及测试。items 模式不得默默只给前几项；真正超过硬预算时返回范围／数量及需缩小范围的事实，不将部分结果冒充完整明细。

知识工具的完整原文及来源继续保存。模型只接收一份必要证据，entries 与拼接 evidence 不重复携带相同原文；source_id、出处及可支撑结论的原文保持对应。历史知识长正文按轮次移出，来源不可由摘要伪造。

普通记餐／改量直接使用对应 meal_totals，不因缩减视图补查全天数据。历史定位需要 items 时一次请求正确详情，不先取 summary 再补同一查询。

## 5. 后台话题摘要

### 5.1 来源与有效结果

沿用当前 DeepSeek 模型及思考模式。摘要仅归并过去的用户意图、已给条件、明确偏好线索和话题背景；不保存生效目标、摄入合计、营养结论、已执行状态或操作授权。摘要标记 fact_scope=dialogue，完整业务状态独立保留。

来源为上一份有效摘要及其后连续的、已完成且不属于近期2轮的清洁对话。以稳定消息 ID 和顺序维护可直接读取的来源及覆盖游标；按最早未覆盖前缀处理，不从中间抽样或只截最后若干字符。模型推理正文及重复工具快照不进入摘要。轮次结束指本次执行终结且回复交付／展示已确认；独立待办或提案可以仍然有效。

临时请求已移出的未覆盖轮次仍在持久来源中，后台不能依赖上一次模型请求内容，也不能靠扫描全部历史执行找回来源。首次升级保留有 dialogue 标记的有效旧摘要作为基准、现存清洁对话作为后缀；无来源标记或已确认的错误占位摘要不能成为有效基准，不为升级重放业务。

一次取尽量接近12,000输入目标的完整轮次；单轮超过目标时可单独处理，但仍受模型硬上限及执行预算约束。无法容纳或处理失败则保留来源，不伪造摘要或跳过该前缀。

每份任务和候选保存会话身份、基于哪份摘要、覆盖起止消息 ID、来源内容摘要及候选正文。覆盖范围由程序确定，不能相信模型自报。输出为空、超1,024正文tokens、被截断或调用失败都不替换历史；禁止把错误字符串作为摘要保存。

### 5.2 调度与应用

消息写入者在完整轮次结束时按第3节阈值登记摘要需求，随现有会话保存可靠提交。每会话最多一个待执行或计算中任务；未开始的需求合并，计算中的输入保持不变，后续新增内容留到下一批。摘要输入快照有界，不能把全会话反复复制到任务中。

复用现有5分钟后台触发和独立归档函数。先处理受理恢复、必要维护与到期归档；本次没有这些任务的待处理错误、且平台剩余时间至少25秒时，至多计算一个会话的摘要。摘要计算最多20秒，至少5秒留给保存结果和退出；没有预算就跳过。维护执行必须取得整次截止时间，不能只设置单个 HTTP 超时。

每个任务最多自动计算2次；成功候选未应用时只重送候选，不重新调用模型。次数用尽自动退出活动任务，仅保留身份、来源边界／哈希及诊断，解除该任务的额外输入快照引用；有效摘要及尚未覆盖的会话来源不变。此后有新的已完成轮次才可重新登记需求，定时器不反复重建同一失败任务。按首次登记顺序选取活动会话，合并不重置其等待顺序。

后台只写独立任务进度和候选，不能直接保存会话；结果通过现有消息写入者的控制事件应用，不发送用户回复、不占用业务模型／工具预算，也不新增用户轮次、业务受理序号或改变 last_message_id／提案展示状态。

应用时核对会话、基准摘要及覆盖前缀：该前缀仍一致且未被更新摘要覆盖时，原子替换对应历史表示、推进覆盖游标并保留所有后续消息。新消息追加本身不使候选失效；旧候选不能回滚较新摘要、设置、待办、提案或会话头。后续前台保存及旧执行恢复也须保留已应用的最新摘要状态，不能回写开始执行时的旧摘要。应用幂等；崩溃恢复复用候选，不重新执行业务。

前台不等待摘要计算。后台未完成或失败时使用现有有效摘要及尚未覆盖的原文，按第3节控制本次输入；不得在回复后继续占用同一个消息执行位生成摘要，也不得在 SCF 返回后启动无人承接的线程。

### 5.3 预设与存储衔接

live 三入口共用上述视图和摘要状态。shadow_readonly 可使用已发布有效摘要，仅读当前可见状态，不创建需求、候选或应用事件。shadow_fakewrite 使用 FakeStore 及注入后台执行器验证同样的语义，不访问云端。

摘要需求、输入快照和候选纳入现有 COS 文档及活动索引，按会话准确发现，不扫描全部完成执行。当前有效摘要及未覆盖的清洁对话属于会话状态；活动任务输入是恢复依赖，成功应用、终止失败或任务被替代后解除额外引用，沿用 COS 保留策略，不由上下文裁剪直接删除对象。不新增人工终结工具。

本轮无需先完成 COS 物理清理，但与其格式升级同时实施时须保留摘要任务和候选的身份、来源与进度。不得将新任务绑定到会被回收的物理前缀而缺少迁移映射。

## 6. 最小验证与交付

沿用 harness/eval/runner.py，先用 --list 选择受影响的 E、CX、LT02 和相关 Pipeline 场景；扩展现有夹具与注入点，不运行历史全量或 COS 迁移／清理验收。未改行为的有效证据复用，修复后仅复验受影响项。

### 6.1 离线必验

| 组 | 必须证明 |
|---|---|
| 请求预算与协议 | 空历史＋巨大状态／当前输入／工具结果也被计入；额外10,000中文 reasoning 字符使计量增加；tools 和 max_tokens 实际进入请求。主／摘要上限分别生效，调用配对不破坏；截断生成不被当作完整成功。硬超限后旧收件终结，新缩小输入可执行，重投不恢复已终止动作。 |
| 投影与聚合 | 固定当日及有效待办，历史从1,000扩大到10,000条，summary 查询的模型输入不随明细线性增长；summary／daily／items 统计一致、定位ID可用。知识证据只出现一次且出处不变；当前工具改变状态后下一次模型看到新视图。 |
| 摘要状态机 | 调用异常、空／过长／截断输出均不删除旧历史；输入保持连续前缀。前台移出未覆盖轮次后，下一批摘要仍能准确读取它们。新消息追加、用户纠正、旧候选迟到、应用中断、重复控制事件及旧执行恢复不丢后缀、不回滚状态、不重复业务。第2次失败自动退出活动任务并解除额外快照引用，无新消息时不再计算。 |
| 调度与能力 | 用阻塞摘要传输证明普通消息无需等待；归档有错误或剩余时间不足时不启动摘要。跨日补全、候选编号、确认／取消、历史改量和旧执行恢复仍正确；只读预设零写。 |
