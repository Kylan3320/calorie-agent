# 个人饮食管理规格

本规格定义个人饮食管理业务；回复行为见 [交流体验规格](CONVERSATION_EXPERIENCE_SPEC.md)，存储与执行见 [COS 规格](LATENCY_OPTIMIZATION_SPEC.md)，实际接口见 [contracts/](contracts/)。

## 1. 目标与范围

日常记账要准确、少追问。饮食规划要给出可照做、可修改的一日菜单，标清依据和估算。完整任务的交付顺序与验收入口见 [交流体验规格](CONVERSATION_EXPERIENCE_SPEC.md#1-目标与范围)。

包含：整餐及部分补全、来源明确的份量换算、常用餐和历史餐复用、指定项纠错与撤销、多轮上下文及压缩、饮食方案计算、目标和偏好管理、可开关的记餐提醒。

范围外：拍照/语音/条码、体重及穿戴设备、购物清单、自动日报/周报、多用户权限、批量清空、新控制台 UI、自动调整摄入目标。

## 2. 技术决策

| 项目 | 要求 |
|---|---|
| 运行时 | LangChain v1 create_agent，使用其 LangGraph 编排与原生 tool calling。工具批次满足交流体验规格的完成条件时直接事实回执，其余请求继续模型决策。 |
| 模型与依赖 | 保留 DeepSeek 及当前配置模型，不迁移产品模型。锁定支持 Linux Python 3.10 的兼容稳定版本，同步 requirements.txt 与打包脚本。 |
| 数据 | COS 保存当前业务事实、个人设置及运行状态，Bitable 后台归档与维护来源；访问统一经 agent/storage/。生产 CosStore 与 FakeStore 保持对应业务语义，详见提速规格。 |
| 食物与知识 | 本地 foods＋薄荷搜索/详情/单位；知识保留 knowledge_retriever 与生产 LightRAG，历史摄入走结构化查询。 |
| 入口 | 飞书、DSH 的 /calorie 和 CLI 使用同一业务运行时；保留 /dsh 引擎及账号别名。DSH 按 session_id 隔离，CLI 交互进程内延续同一会话。 |
| 预设 | live 经统一 COS 通道真实读写，Bitable 后台归档；shadow_fakewrite 使用 FakeStore，不访问真实存储；shadow_readonly 读取已提交 COS 事实，对 COS、Bitable、投递及 usage 零写入。后两者不发送飞书消息。 |
| 部署 | 腾讯 SCF，Python 3.10、主入口端口 9000；提醒使用 SCF 定时触发，不引入常驻调度器。 |

从注册表中的工具对象派生名称、description、参数 schema、风险和执行函数，按预设筛选后作为原生 tools 传入每次模型请求；系统 prompt 只保留共用规则，不手写另一份工具说明。模型选择工具、解释用户意图；后端绑定身份、动作标识、目标引用和确认状态；工具负责匹配、计算及存储。

模型通过原生工具循环决定行动。业务实现复用既有工具，不引入产品内子 Agent、Skill 加载或另一套记忆框架。

## 3. 行为规则

### 3.1 整餐与补全

- record_meal 一次接收多项食物。食物匹配、份量换算、营养计算和批量写入在工具内完成，不逐食物调用模型。
- 可确定的项先记录；其余项保存原文、原日期/餐次、已知数量和候选，合并询问缺项。后续只补未完成项；用户换话题时保留它们，取消时仅取消未完成项。
- 明确匹配要求名称或已确认别名及用户已给特征相符，且无冲突候选。搜索只返回一条、排名第一或模型自报置信度均不能单独作为匹配依据。仅实际的食物种类、生熟或单位歧义才询问。
- 候选编号绑定该未完成项已展示的候选快照；选定后接续原餐，数量已知就直接记录。缺营养依据时补查或询问可核实的信息，不由模型生成每100g营养。
- 未提供餐次保存 unknown，不为餐次额外追问。相对日期按原消息接收时的本地日期解析；补全跨日和重试均保留原餐日期，用户明确改日期时除外。
- 回执列实际完成项、必要的估算标记及合并后的缺项，不在每次记录后自动追加建议或问题。

### 3.2 份量与营养

记餐按用户本次明确的可食克重、已确认的常用份量、薄荷该食物唯一匹配的单位顺序取值，仍无依据时询问。规划中的建议份量及外卖估算按第3.6节处理。数量、比例及单位换算均由工具执行。

- 本地资料不足时经 storage 查询薄荷；有 boohee_id 则用 code 请求 GET /v1/food/detail、with_units=true，必要时再用 GET /v1/food/units。缓存完整则复用；旧 foods 按需补齐，不跨食物套用单位。
- 营养按可食重 eat_weight 缩放。只有总重 weight 且没有可食依据时询问，不猜可食比例。使用个/碗/份等换算时标注“估算”，保存数量原文、来源及最终可食克重。
- 用户明确要求保存的份量才长期生效。接口或权限不可用时用已确认个人份量；仍无依据则保留该项并询问，不购买或升级套餐。
- 优先使用来源每100g热量；缺失时按未舍入的碳水×4＋蛋白质×4＋脂肪×9计算，并标记来源。计算后按现有 round_number 口径保存展示；汇总使用有效摄入快照，不重新套用宏量营养公式生成热量。
- 新摄入保存食物、每100g营养、数量与换算依据及最终营养快照。旧摄入保持原值；旧 foods 缺来源热量时可继续使用公式口径。

### 3.3 复用、纠错与确认

- “昨天午饭一样”读取对应日期/餐次的有效明细；目标存在多个不相干批次且无法确定时询问。常用餐由用户明确命名保存食物、份量和营养依据快照；复用按原快照及指定比例新增，日期为本次指定日期或接收日期。
- 显式指定多条摄入保存常用餐或复用时，按原顺序逐项核对本人的有效记录。任一项无效则整次保存／复用不生效，原同名常用餐和账本保持原值。回复指出可辨认的缺项，保留本会话原选择供修订。用户明确缩小范围后按新范围执行，再次复用以实际保存的整份快照为准。这条完整性规则与普通整餐记录允许部分完成分别执行。
- “刚记的／刚才那份”以本人当前会话最近实际记入的餐为范围，再按用户说的餐次、食物及其他限定定位。当前引用已唯一指向有效记录时，首轮直接用 revise_intake，工具核对原 ID 和归属，按原营养快照改量或软删除。浏览历史、看菜单不改变最近记餐。仅说“今天早餐”时按该日餐次定位，不默认最后一碗。引用不足时按所需范围查一次 items，仍有多个匹配就展示可区分选项，待选定才写。成功回执采用原餐更新后的合计。
- 明确要求记录、保存设置、改目标、配置提醒时直接执行。模型主动提出的写入建议保存为待确认提案，尚不修改目标、摄入等业务事实。
- 单独“确认/好的”仅执行上一条助手回复明确请求确认的提案；提案绑定展示过的目标和参数。用户修订参数时按修订内容处理；取消即作废，不据无关回复或模型参数里的 approved 标志授权。
- 提出计划、确认采用计划与报告食用分别处理；只有明确报告已食用或要求记录才写摄入。

### 3.4 工具与事实输出

| 工具 | 职责 |
|---|---|
| record_meal | 整餐新增、未完成项补全/取消、按历史餐/常用餐及比例新增。 |
| revise_intake | 指定摄入项改量或软删除。 |
| query_today | 今日有效摄入、逐字段生效的目标及剩余。 |
| query_history | 指定时间窗聚合，按需返回餐食明细和可操作记录引用。 |
| query_food_nutrition | 指定摄入读取对应快照。食物资料查询及计划核算共享可续用的食物来源引用。 |
| query_knowledge | 静态知识检索，返回原文证据和来源。 |
| calculate_meal | 按第3.6节核算整日菜单或今日剩余安排，区分已核实、按假设估算及未计入的餐项。 |
| update_user_settings | 更新指定目标、偏好、常用份量、常用餐或提醒规则；不写摄入。 |

相关设置随上下文读取，不增读取工具；营养查询/方案计算可在允许写入的预设中填充食物资料缓存，不能创建摄入或个人设置。工具内部完成 API 搜索、单位查询和存储，不再把这些步骤暴露为模型工具。

营养查询返回的每个可用候选带名称、可区分特征及可由营养查询和计划计算消费的来源引用，绑定本会话实际返回的食物或快照。展示“选哪项”时同条给出可辨认选项，并保留已展示顺序供下一轮“第2个”接续。工具接受该来源引用并核对身份及份量依据。资料缺失、引用无效或误传记餐选择号时，返回可纠正的工具结果，标明可用来源或应询问的缺项，允许在原预算内继续。记餐候选继续绑定原摄入待办，规划／资料查询使用自己的食物参数，工具只声明自己能够执行的选项。

工具结果区分成功项、未完成项和错误，携带可展示数值的字段、对象、日期及来源。普通账本及只改已展示菜单的完成条件见[交流体验规格第2.2节](CONVERSATION_EXPERIENCE_SPEC.md#22-直接回执的完成条件)。知识数字及具体证据性结论使用模型本次可见、可唯一定位原文和出处的检索证据，包括仍可见的上轮原文。引用规则见[第4.2节](CONVERSATION_EXPERIENCE_SPEC.md#42-查询结果)。

已记录/修改/撤销/设置生效须对应相应成功事实。缺项、提案和失败不能宣称成功；部分成功分别说明。摘要、用户参数、ID 和评分不提供营养数值依据；不增加额外 LLM 审核器。

### 3.5 会话、压缩与恢复

- 会话按归一 user_id＋入口会话 ID 隔离；个人设置按归一 user_id 共享。同一会话按收件顺序处理，后续消息读取前一条的已保存状态。
- 飞书持久化原消息、接收时间和日期后快速 ACK，再执行模型。收件、对话、未完成项、记录/提案引用、工具调用及结果属于同一套可恢复状态，经 Store 保存；进程重建后仅从 Store 即可继续。
- 模型上下文包含系统规则、可用 tools、相关设置、最近完整对话、较早摘要和相关未完成事项/引用。账本与知识按需查询，不预载全部历史；摘要不替代独立保存的未完成项和执行事实。
- 上下文采用近期清洁对话、后台摘要和结构化状态；当前逻辑消息及配对工具结果完整保留。模型历史视图、摘要来源及恢复规则见 [交流体验规格](CONVERSATION_EXPERIENCE_SPEC.md)，使用标准消息序列化，不自建 checkpoint 后端。
- 每次模型返回的工具批次先保存参数、固定动作标识及完成声明，再按返回顺序执行并逐项保存结果。满足整轮完成条件时直接事实回复，否则在剩余预算内继续原生循环，不预先固定整条消息的后续计划。
- 重试重用已保存调用与结果，跳过成功动作；剩余预算内未完成调用仍用原参数、目标和日期。预算耗尽后只核对既有提交及恢复交付，不重新规划或复活已终止动作。创建防重沿用 bitable_schema 的键公式与动作序号，更新固定 record_id。
- 保留显式恢复入口 app.py --retry-pending，恢复未完成收件、执行及待发送回复。发送前保存最终回复，重发使用同一回复及 uuid，不重新生成已完成回复。
- 模型与工具预算沿逻辑消息累计；等待、终止及恢复按 [交流体验规格第2节](CONVERSATION_EXPERIENCE_SPEC.md#2-回复完成与恢复)。预算到期不把未知提交判为失败，摘要独立使用后台预算。

### 3.6 饮食计划与草案

1. **先定范围。** “每天怎么吃”使用默认及长期目标，不扣今天的摄入。“给今天做完整菜单”使用该日生效目标，也不扣已吃。“今天还可以怎么吃”使用该日目标，扣一次当日有效摄入，再扣拟新增餐项。由模型随原调用明确此范围，工具返回实际目标、计入的摄入范围及差额。已保存的旧调用缺范围时沿用原增量口径。
2. **先算固定餐。** 标明固定餐、排除配料、可调整的食材／份量和烹饪条件。“优先使用包括但不限于”给出可选范围。工具先按来源、可食份量、重复份数计算固定餐的热量及碳水、蛋白质、脂肪小计。补充食物的缺口＝适用目标－本范围应扣的已食用摄入－尚未计入的固定餐。整日计划不扣账本，今日剩余只扣一次有效摄入，已吃的餐也不能再作为拟新增餐扣一次。保留有符号的缺口，负数表示固定部分已超过对应目标。
3. **再按缺口搭配。** 用上述缺口选可获取、易准备的补充项及份量。每100克营养和日常单位换算取自来源。分别标注用户明确份量、建议份量和外卖组成假设。外卖配方无法核实时可按有来源的组成拆分估算。关键组成无法计入时，只给小计、遗漏项及一个能推进计划的问题。
4. **工具定份量。** 模型选食材、标出固定项和可调建议量。calculate_meal 在同次调用内用已解析的来源核算，已有初稿和备选都可作为起点。完整方案已落入用户容差时从中选版。全都超差时，先调一项建议量，仍超差或达标须增大某项宏量偏差时，再比较两项互补调整。只改已有补充项每份的建议量，保持固定组成、明确给定的份量、排除项、份数、做法和上限。按来源的日常单位或便于称取的整克档位取正份量，展示的数量须能复算。指定项改稿只能在第6项的范围内调量。用户未给容差时沿用原目标与差额口径。校正不增加模型调用、外部查询或新食材。

   校正候选从原建议量到最近容差边界，取来源日常单位或10克称量档位；模型建议量距来源整数单位不超过1克时可识别该单位，实际校正仍使用来源精确可食重，不更改用户固定量。两项互补只扩至另一项单位步长溢出所需范围，不作全域宏量优化。无日常单位且上限不足10克时使用可称取正整克。既有初稿与备选按原规则选起点，校正已有版本达标后不再扩大搜索。

   完整且在容差内优先。容差内先排除三项宏量绝对偏差均不优且至少一项更差的方案。其余按最差宏量相对偏差（仅计正目标）、用户份量与备餐偏好依次选择，并列时保留原建议。无需继续追求热量零误差。可调范围内仍未找到达标量时，给出找到的最接近目标的完整菜单、实算差额及起限制作用的条件。缺来源按第3项只给小计。保留原建议与选中量、固定小计和前后差额供核对；校正后数量文字按同来源换算同步，原文字保留审计，做法和组成条件保留，公开菜单只列最终量。
5. **显示与接续同一草案。** 最终只展示选定菜单一次，按餐给食物、份量、必要假设及汇总差额。相同午晚餐可写一份清单并注明两餐各一份。显示用的份量可合理舍入，重算使用原来源与未舍入依据。自由文本假设只公开组成和做法等定性部分；数量句保留审计，公开数量统一取已解析菜单，避免近似“几个”或错附其他食物的数量与实算相冲突。固定餐带假设时明确组成估算，不称为用户给定量。只有实际需要选择时展示候选及编号。模型可补充一句理由或取舍，逐项明细由同一草案生成。未选方案、中间小计、已解决的营养查询选项不作为另一份菜单或可续选选项发布。
6. **只改用户指定的项。** 按用户＋会话把实际交付的菜单与草案身份绑定，未交付稿、恢复事件或迟到展示不得覆盖已展示新版。“把鸡胸换成鸡蛋”从该草案定位全部相应餐次，按有来源的鸡蛋份量替换并重算，只产生一份新稿。保留其余餐项、份数、原假设及限制。没有鸡胸时明确说明并保留原稿，必要时问想替换哪项。替换造成冲突时先交代差额，再由用户决定是否扩大调整范围。规划、改稿和确认采用均不写摄入。

### 3.7 目标与提醒

- 生效目标逐字段按“项目默认值→长期设置→当日设置”覆盖。明确修改只更新指定字段；支持今天或长期，未指范围时长期。修改长期值不覆盖已有当日值，次日不再使用前一日覆盖值。
- 提醒规则为启停、餐次、HH:MM 和星期，默认关闭，时区使用项目配置，未指定星期为每天。请求启用但缺条件时保存同一条关闭规则，回执说明已保存、尚未启用及实际缺项。同一会话保留这次启用意图、规则身份和缺项。下一句“12点”补原规则，重新核对条件后只启用一次。取消、规则变化或指代冲突时不沿用失效的启用意图。缺飞书会话时说明需在哪个入口完成绑定。
- SCF 每分钟触发，以计划触发时间所在的本地分钟匹配规则；仅已启用且当日对应餐次无有效记录时发送。同规则同日一次，关闭后下一次检查停止，不补发往日提醒。使用事实模板，不调用模型。
- 目标为后端保存的本人最近一次飞书会话；缺该会话则提示先与机器人发起会话，规则保持关闭。规则 ID＋本地日期生成固定消息键，沿用回复 uuid 防重并保存发送结果。DSH 聊天回复不发送到飞书。
