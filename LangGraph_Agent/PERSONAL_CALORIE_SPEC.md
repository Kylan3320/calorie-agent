后续交流体验改进的已确认目标及验收见 [CONVERSATION_EXPERIENCE_SPEC.md](CONVERSATION_EXPERIENCE_SPEC.md)，尚待实施；本文件保留前次业务规格及交付范围。

## 1. 目标与范围

首要目标：更少输入和追问，记准每一餐。食物与份量可确定时，一条消息完成整餐记录；补全、纠错和复用不重复索要已知信息。

包含：整餐及部分补全、来源明确的份量换算、常用餐和历史餐复用、指定项纠错与撤销、多轮上下文及压缩、饮食方案计算、目标和偏好管理、可开关的记餐提醒。

范围外：拍照/语音/条码、体重及穿戴设备、购物清单、自动日报/周报、多用户权限、批量清空、新控制台 UI、自动调整摄入目标。

## 2. 技术决策

| 项目 | 要求 |
|---|---|
| 运行时 | LangChain v1 create_agent，使用其 LangGraph 编排与原生 tool calling。模型收到工具结果后决定下一步或结束。 |
| 模型与依赖 | 保留 DeepSeek 及当前配置模型，不迁移产品模型。锁定支持 Linux Python 3.10 的兼容稳定版本，同步 requirements.txt 与打包脚本。 |
| 数据 | Bitable 是业务、个人设置和会话状态的持久存储；访问统一经 agent/storage/。BitableStore 与 FakeStore 保持对应业务语义。 |
| 食物与知识 | 本地 foods＋薄荷搜索/详情/单位；知识保留 knowledge_retriever 与生产 LightRAG，历史摄入走结构化查询。 |
| 入口 | 飞书、DSH 的 /calorie 和 CLI 使用同一业务运行时；保留 /dsh 引擎及账号别名。DSH 按 session_id 隔离，CLI 交互进程内延续同一会话。 |
| 预设 | live 真实读写；shadow_fakewrite 使用 FakeStore，不访问真实 Bitable；shadow_readonly 对真实 Bitable 完全只读，包括会话、追问和 usage。后两者不发送飞书消息；只读会话状态仅在本次运行内保存。 |
| 部署 | 腾讯 SCF，Python 3.10、主入口端口 9000；提醒使用 SCF 定时触发，不引入常驻调度器。 |

从注册表中的工具对象派生名称、description、参数 schema、风险和执行函数，按预设筛选后作为原生 tools 传入每次模型请求；系统 prompt 只保留共用规则，不手写另一份工具说明。模型选择工具、解释用户意图；后端绑定身份、动作标识、目标引用和确认状态；工具负责匹配、计算及存储。

移除规则命中后绕过模型、固定全消息 AgentPlan 及其旧执行/追问分支。保留可复用的业务实现，不增加旧协议兼容层、工具搜索、Skill 加载、产品内子 Agent 或另一套记忆框架。

## 3. 行为规则

### 3.1 整餐与补全

- record_meal 一次接收多项食物。食物匹配、份量换算、营养计算和批量写入在工具内完成，不逐食物调用模型。
- 可确定的项先记录；其余项保存原文、原日期/餐次、已知数量和候选，合并询问缺项。后续只补未完成项；用户换话题时保留它们，取消时仅取消未完成项。
- 明确匹配要求名称或已确认别名及用户已给特征相符，且无冲突候选。搜索只返回一条、排名第一或模型自报置信度均不能单独作为匹配依据。仅实际的食物种类、生熟或单位歧义才询问。
- 候选编号绑定该未完成项已展示的候选快照；选定后接续原餐，数量已知就直接记录。缺营养依据时补查或询问可核实的信息，不由模型生成每100g营养。
- 未提供餐次保存 unknown，不为餐次额外追问。相对日期按原消息接收时的本地日期解析；补全跨日和重试均保留原餐日期，用户明确改日期时除外。
- 回执列实际完成项、必要的估算标记及合并后的缺项，不在每次记录后自动追加建议或问题。

### 3.2 份量与营养

份量顺序：用户本次明确的可食克重 → 该食物及单位的已确认常用份量 → 薄荷该食物唯一匹配的单位 → 询问。数量、比例及单位换算均由工具执行。

- 本地资料不足时经 storage 查询薄荷；有 boohee_id 则用 code 请求 GET /v1/food/detail、with_units=true，必要时再用 GET /v1/food/units。缓存完整则复用；旧 foods 按需补齐，不跨食物套用单位。
- 营养按可食重 eat_weight 缩放。只有总重 weight 且没有可食依据时询问，不猜可食比例。使用个/碗/份等换算时标注“估算”，保存数量原文、来源及最终可食克重。
- 用户明确要求保存的份量才长期生效。接口或权限不可用时用已确认个人份量；仍无依据则保留该项并询问，不购买或升级套餐。
- 优先使用来源每100g热量；缺失时按未舍入的碳水×4＋蛋白质×4＋脂肪×9计算，并标记来源。计算后按现有 round_number 口径保存展示；汇总使用有效摄入快照，不重新套用宏量营养公式生成热量。
- 新摄入保存食物、每100g营养、数量与换算依据及最终营养快照。旧摄入保持原值；旧 foods 缺来源热量时可继续使用公式口径。

### 3.3 复用、纠错与确认

- “昨天午饭一样”读取对应日期/餐次的有效明细；目标存在多个不相干批次且无法确定时询问。常用餐由用户明确命名保存食物、份量和营养依据快照；复用按原快照及指定比例新增，日期为本次指定日期或接收日期。
- “刚才那份”从当前会话记录引用定位；指定项的修改/删除/撤销直接执行，目标不唯一才询问。改量接受明确克重、单位或比例，按该记录原营养依据重算；删除为软删除，不影响其他项。
- 明确要求记录、保存设置、改目标、配置提醒时直接执行。模型主动提出的写入建议保存为待确认提案，尚不修改目标、摄入等业务事实。
- 单独“确认/好的”仅执行上一条助手回复明确请求确认的提案；提案绑定展示过的目标和参数。用户修订参数时按修订内容处理；取消即作废，不据无关回复或模型参数里的 approved 标志授权。
- 提出计划、确认采用计划与报告食用分别处理；只有明确报告已食用或要求记录才写摄入。

### 3.4 工具与事实输出

| 工具 | 职责 |
|---|---|
| record_meal | 整餐新增、未完成项补全/取消、按历史餐/常用餐及比例新增；替代 record_food。 |
| revise_intake | 指定摄入项改量或软删除；替代 undo_last。 |
| query_today | 今日有效摄入、逐字段生效的目标及剩余。 |
| query_history | 指定时间窗聚合，按需返回餐食明细和可操作记录引用。 |
| query_food_nutrition | 指定摄入优先读快照；一般食物查询使用食物资料及工具计算。 |
| query_knowledge | 静态知识检索，返回原文证据和来源。 |
| calculate_meal | 方案的逐项营养、合计及预算差额，不写摄入。 |
| update_user_settings | 更新指定目标、偏好、常用份量、常用餐或提醒规则；不写摄入。 |

相关设置随上下文读取，不增读取工具；营养查询/方案计算可在允许写入的预设中填充食物资料缓存，不能创建摄入或个人设置。工具内部完成 API 搜索、单位查询和存储，不再把这些步骤暴露为模型工具。

工具结果区分成功项、未完成项和错误，携带可展示数值的字段、对象、日期及来源。模型组织正文，业务数值片段由上述字段填入；守卫核对字段引用及成功状态，不以整个回复等于固定模板或数字集合命中为通过条件。知识可综合表达，数字及结论须有本轮检索证据并保留来源。

已记录/修改/撤销/设置生效须对应相应成功事实。缺项、提案和失败不能宣称成功；部分成功分别说明。摘要、用户参数、ID 和评分不提供营养数值依据；不增加额外 LLM 审核器。

### 3.5 会话、压缩与恢复

- 会话按归一 user_id＋入口会话 ID 隔离；个人设置按归一 user_id 共享。同一会话按收件顺序处理，后续消息读取前一条的已保存状态。
- 飞书持久化原消息、接收时间和日期后快速 ACK，再执行模型。收件、对话、未完成项、记录/提案引用、工具调用及结果属于同一套可恢复状态，经 Store 保存；进程重建后仅从 Store 即可继续。
- 模型上下文包含系统规则、可用 tools、相关设置、最近完整对话、较早摘要和相关未完成事项/引用。账本与知识按需查询，不预载全部历史；摘要不替代独立保存的未完成项和执行事实。
- 用内置 SummarizationMiddleware，历史约 12000 tokens 时触发，保留最近约 4000 tokens 的完整对话及配对工具调用/结果，阈值放 config.yaml。复用标准消息序列化保存摘要及保留消息，不自建 LangGraph checkpoint 后端。
- 每次模型返回的工具调用先保存参数及固定动作标识，再按返回顺序执行并逐项保存结果；同一批工具调用串行执行。模型收到结果后继续决策，不预先固定整条消息的后续计划。
- 重试重用已保存调用与结果，跳过成功动作；未完成调用仍用原参数、目标和日期。尚未生成的后续步骤可在恢复后继续调用模型。创建防重沿用 bitable_schema 的键公式与动作序号，更新固定 record_id；只替换旧状态链，不并行维护旧 AgentPlan/pending 路由。
- 保留显式恢复入口 app.py --retry-pending，恢复未完成收件、执行及待发送回复。发送前保存最终回复，重发使用同一回复及 uuid，不重新生成已完成回复。
- 单条消息默认最多 4 次主决策模型调用、8 次工具调用和 90 秒处理期限；摘要调用仅在压缩触发时额外发生。调用次数用内置 middleware 限制，不叠加自动重试 middleware；到限保留进度，以已有事实返回完成/未完成情况，不额外调用模型润色。

### 3.6 目标、计划与提醒

- 生效目标逐字段按“项目默认值→长期设置→当日设置”覆盖。明确修改只更新指定字段；支持今天或长期，未指范围时长期。修改长期值不覆盖已有当日值，次日不再使用前一日覆盖值。
- 计划读取当前目标、摄入和偏好；模型提出组合，calculate_meal 计算后才展示营养数字。替换食物或份量后重新计算，无法满足明确限制时报告缺口。
- 提醒规则为启停、餐次、HH:MM 和星期，默认关闭，时区使用项目配置。未指定星期为每天；启用时缺时间或餐次则合并询问，不自行设定。飞书与 DSH 均可用自然语言配置。
- SCF 每分钟触发，以计划触发时间所在的本地分钟匹配规则；仅已启用且当日对应餐次无有效记录时发送。同规则同日一次，关闭后下一次检查停止，不补发往日提醒。使用事实模板，不调用模型。
- 目标为后端保存的本人最近一次飞书会话；缺该会话则提示先与机器人发起会话，规则保持关闭。规则 ID＋本地日期生成固定消息键，沿用回复 uuid 防重并保存发送结果。DSH 聊天回复不发送到飞书。

## 4. 执行与发布

一个主线程连续实现及集成，不另开实现线程串行接力；独立读取和确定性检查用工具批量执行。按下表顺序推进，不为中间阶段接回旧协议增加过渡层，批次间不等待重复确认。

| 阶段 | 可交付结果 |
|---|---|
| A：新链路闭环 | 固定工具/Store/会话状态契约，接入 create_agent 及原生工具结果循环；用明确克重的整餐记录和查询跑通存储、事实回复及重复消息处理。 |
| B：业务补齐 | 薄荷详情/单位、来源热量、部分补全、复用/纠错、设置/目标/计划、上下文压缩；同步 Store 两实现、三预设、DSH/CLI、trace 消费者并删除替代的旧分支。 |
| C：发布准备 | 提醒及恢复入口、Linux Python 3.10 部署包；完成第 5 节离线场景和构建检查，同步 REQUIREMENTS、相关 contracts 与 README 操作入口。 |
| 审查 | 一个未参与实现的只读子 Agent 核对最终改动、验收证据和受影响入口，只报有位置、触发条件和实际影响的缺陷；不改文件、不再委派、不扩充验收范围。主线程修复成立的问题，仅复验受影响场景。 |
| D：上线交付 | 主线程执行必要表结构更新、旧状态收尾、SCF 发布、真实飞书验收及本次测试数据清理。 |

主函数固定 ap-shanghai/default/calorie-agent-api-v3-test；飞书应用“热量agent-v3”（cli_aabc166fccb8dcef），保持其现有 webhook 地址。另建同地域/命名空间的 calorie-agent-reminder 定时函数，复用业务包并绑定提醒处理入口；不修改其他云函数。

表结构变更经 storage，在发布阶段执行并保留既有业务数据。切换前通过旧入口收尾已收件的执行和回复；尚待用户回答的追问只迁移原日期、数量、候选及目标等事实到新状态，关闭对应旧任务，不将旧计划协议带入新运行时。

保留生产知识索引和实际 LightRAG 配置；依赖兼容需要时可更新 Layer。同步部署包与依赖，控制台依赖和构建产物不进包。主函数超时至少 120 秒；health 显示构建标识、实际模型及检索器。只改本次需要的环境变量和绑定，不输出密钥。

## 5. 最小必要验收

复用 harness/eval/runner.py；仅选择下列场景，已有用例可替换实现或复用。各场景用独立 FakeStore、假时钟、原生 tool-calling 假模型及假薄荷传输，预期值来自固定夹具，不从待验工具结果反算。只运行必要场景，不要求全量评测、先跑 smoke 基线、覆盖率目标、压测、模型横评或新测试框架。通过后仅在后续改动影响该行为时复验，不增加阶段测试集。

| 编号 | 场景与通过标准 |
|---|---|
| U01 | 夹具 A 每100g：碳水10g/蛋白2g/脂肪1g/60kcal；B：0g/12g/10g/150kcal，每个总重60g、可食重50g。记录 A200g＋B2个，无追问；B 为100g且标估算，A120kcal、B150kcal，合计碳水20g/蛋白16g/脂肪12g/270kcal，实际快照及回复一致。 |
| U02 | 整餐中一项可记、另两项分别待选候选及缺份量：已知项先写，缺项合并问；补数量、选候选并跨日继续后，沿用原信息/日期，原餐全部完成且没有重复行；一个搜索结果不因数量为一就消除语义歧义。 |
| U03 | 独立记录 U01 同款餐并保存为常用餐→新增半份→将新增的 A 改为50g→撤销新增的 B→查询：原餐保持270kcal、新增剩 A 为30kcal、合计300kcal，仅3项有效；复用不重查已保存营养依据，不要求重输整餐。 |
| U04 | 混合记餐/知识问答并接指代追问，强制一次压缩后清空进程内会话、从 Store 重建：意图及引用/未完项可继续；模型请求含注册表派生的工具说明/schema，后续决策收到先前工具结果。另一会话不继承本会话 pending；只读预设不写任何 Bitable 状态。 |
| U05 | 明确改目标/保存偏好直接生效且只改指定字段，今日覆盖与长期目标各自生效；模型提案未确认不生效，“好的”仅确认紧邻提案。计划数字来自 calculate_meal，未报告食用不写摄入，明确记录后才写。 |
| U06 | 假时钟覆盖关闭、到期未记餐、重复触发、已记餐：发送次数依次为0/1/不增加/0，目标为保存的本人飞书会话；缺时间/餐次或投递目标时不启用，常规提醒无模型调用。 |
| U07 | 一条消息含连续两次写入，在首次写入成功但结果未保存时模拟失败，再重建恢复并重复投递：两动作各生效一次，原日期/目标不变，后续动作未丢失；回复发送失败后重用已存回复及 uuid。 |

发布只补以下检查，不重复另建验证流程：

1. Linux Python 3.10 下构建并启动实际部署包一次，确认新 Agent、检索器和提醒入口可加载；发布后 health 标识与该包一致。
2. 用现有 BOOHEE_API_KEY 搜索一种食物并查带 units 的详情，核对来源热量、单位与可食重；权限不足则采用已确认个人份量回退，记录实际状态，不扩展供应商或套餐。
3. 一组真实飞书对话完成“整餐→改单项并保存常用餐→按比例复用并查询→知识问答”。核对实际 Bitable 行及回复；trace 须证明当前 DeepSeek 进行了原生工具选择、工具结果回传及后续决策，知识查询实际使用 LightRAG。不能以旧规划器、静态回复或 FAQ 替代。凭据/权限缺失时只询问缺失配置。
4. 核对定时触发器已启用、绑定提醒入口、用户提醒默认关闭及日志可见；发送分支由 U06 验收，不额外等待线上定时发送。

验收后只软删除本次新增摄入、移除本次验收常用餐并恢复变动设置。交付构建标识、场景结果、真实飞书/Bitable 结果和实际份量来源；有未完成项则列出，不标记整体完成。
