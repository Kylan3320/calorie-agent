# Personal Calorie Agent 升级规格

状态：已确认目标，待实现。交付包括代码、必要验收、腾讯云发布和本人飞书实测。
需求基线见 [REQUIREMENTS.md](REQUIREMENTS.md)；跨模块接口在对应批次实现时同步到 [contracts/](contracts/)。

## 1. 目标与范围

首要目标：更少输入和追问，记准每一餐。明确食物及数量的一条消息完成整餐记录；已经提供的信息不重复索要。

本次包含：整餐记录、来源明确的份量换算、候选补全、常用餐及历史餐复用、单项纠错与撤销、多轮上下文及压缩、饮食方案计算、目标和偏好管理、可开关的记餐提醒。

不包含：拍照/语音/条码识别、体重及穿戴设备接入、购物清单、自动周报、多用户权限、批量清空记录、新控制台 UI、自动调整摄入目标。

## 2. 技术决策

| 项目 | 执行要求 |
|---|---|
| Agent 运行时 | 使用 LangChain v1 的 create_agent，保留其 LangGraph 编排；原生 tool calling，工具结果返回模型后继续或结束。 |
| 依赖 | 使用支持 Python 3.10 的稳定版本并锁定；同步 requirements.txt 与 Linux 打包脚本。通用压缩和调用次数限制使用内置 middleware。 |
| 模型 | 保留 DeepSeek 及当前配置的模型；GPT-6 建议用于本规格与执行方式，不迁移产品模型。 |
| 数据 | Bitable 保存业务事实、个人设置和会话状态；所有访问经 agent/storage/。FakeStore 保持对应业务语义。 |
| 食物数据 | 复用本地 foods 和薄荷官方搜索、详情/单位接口；不接薄荷饮食记录存储。 |
| 知识 | 保留 knowledge_retriever 与生产 LightRAG；历史摄入走结构化查询。 |
| 入口 | 飞书、DSH 和 CLI 使用同一业务入口；保留账号别名，DSH 会话不互相串上下文。live 真实读写并回复，shadow_fakewrite 仅写 FakeStore 且不发送，shadow_readonly 对真实 Bitable 只读且不发送。 |
| 部署 | 腾讯 SCF，Python 3.10，端口 9000；记餐提醒用 SCF 定时入口，不使用常驻进程调度器。 |

生产语义选择统一由模型承担。移除“规则命中即跳过模型”、固定全消息 AgentPlan 协议及其旧执行分支；不为旧协议增加兼容层。现有食物匹配、营养计算和存储代码按新业务规则复用。

工具对象是名称、用途、参数 schema、风险和执行函数的唯一来源；按预设过滤后提供给模型。风险等级、用户身份、动作标识及确认状态由后端决定。首版提供完整的小型工具集，不增加工具搜索、Skill 加载、子 Agent 或另一套记忆框架。

## 3. 业务规则

### 3.1 整餐与补全

- 一次记录调用接受多个食物；匹配、份量换算和营养计算在工具内完成，不逐食物调用模型。
- 已明确的项目直接记录；未确定项目保留原文、日期、餐次、数量及候选，合并询问缺项。后续只完成未记录项目。
- 本地或薄荷结果唯一明确时直接使用；存在食物种类、生熟状态或单位的实际歧义时才询问，不以模型自报置信度代替匹配依据。
- 候选编号绑定已展示的候选快照。用户选定后接续原餐；数量已知时直接记录，不要求重发“食物＋克重”。
- 用户未提供餐次时可保存 unknown，不为餐次额外追问。相对日期以消息接收时的本地日期为准，重试不改变记录日期。
- 记录回执简短，列出实际完成项、必要的估算标记和仍缺的信息；不在每次记餐后自动追加建议或问题。

### 3.2 份量与营养

按以下顺序解析份量：用户明确的可食克重 → 用户为该食物确认的常用份量 → 薄荷该食物唯一匹配的扩展单位 → 询问缺失份量。

- 本地缺少来源热量或单位时，优先调用食物详情 GET /v1/food/detail，传 code 和 with_units=true；需要时使用 GET /v1/food/units。已有 boohee_id 的旧 foods 按需补齐，完整缓存直接复用。缓存按食物编码和单位归属，不能把其他食物的“一碗”套用过来。
- 薄荷单位区分 weight 与 eat_weight；营养按可食重量缩放。无可食重时，只使用明确属于可食重量的单位，不从总重猜可食比例。
- 用“个、碗、份”换算的记录标注估算，保存数量原文、换算来源和最终可食克重。用户明确要求保存的常用份量才长期生效；单次份量说明不自动升级为长期设置。
- 权限不足或接口不可用时，使用已确认的个人份量；仍无依据则询问。保留原餐信息，不购买或升级薄荷套餐。
- 保存来源提供的每100g热量；有原始热量时直接缩放，缺失时才按碳水×4＋蛋白质×4＋脂肪×9计算，并标记计算来源。使用未舍入值计算，最终按现有 round_number 口径保存和展示。
- 新记录保存当时的食物、每100g营养、份量依据及摄入快照；旧记录不因食物库更新而重算。旧 foods 缺少新增字段时继续使用原计算口径，不批量覆盖历史。

### 3.3 复用、纠错与自主程度

- “昨天午饭一样”读取对应日期/餐次的有效明细；同餐多个不相干批次且无法确定时询问目标。常用餐由用户明确命名保存，后续可按整份或比例复用。
- “米饭减半”等比例调整由工具计算；“刚才那份”只从当前会话的记录引用定位，不从聊天摘要猜 record_id。
- 明确目标的修改、删除或撤销直接执行；改量须有明确新数量，目标不唯一才询问。撤销为软删除，数量修改使用该记录的原营养依据计算，仅影响指定项。
- 用户明确要求记餐、保存偏好/份量/常用餐、改目标、设置或关闭提醒时直接执行；模型主动提出的新目标或其他写入建议，先保存为待确认提案。
- 单独的“确认/好的”仅在上一条助手回复请求确认时执行其对应提案；目标和参数固定为已展示内容。其他情形不据此写入。
- 饮食计划、确认采用计划与实际吃下分开处理；只有用户明确报告已食用或要求记录时才写摄入。

### 3.4 工具边界

| 工具 | 职责 |
|---|---|
| record_meal | 新增整餐、补全原餐、按历史餐或常用餐及比例新增记录；替代 record_food。 |
| revise_intake | 修改指定摄入项的数量或软删除；替代 undo_last。 |
| query_today | 今日有效摄入、目标和剩余。 |
| query_history | 历史聚合及按需返回的餐食明细、记录引用。 |
| query_food_nutrition | 食物营养查询，保持摄入快照优先。 |
| query_knowledge | 检索静态知识，返回原文证据和来源。 |
| calculate_meal | 对拟定食物及份量进行营养、合计和预算差额计算，不写摄入。 |
| update_user_settings | 更新用户明确指定的目标、偏好、常用份量、常用餐或提醒规则。 |

设置读取随相关上下文加载，不另加读取工具。模型不得传入营养计算结果充当事实；API 级搜索、单位查询和批量存储留在工具内部。工具失败返回明确状态，成功部分与未完成部分分别陈述。

### 3.5 会话与回复

- 会话按归一 user_id＋入口会话 ID 隔离；长期个人设置按归一 user_id 共享。Bitable 会话在云函数实例重建后可继续。
- 飞书先持久化原消息和接收日期，再快速 ACK；ACK 不等待模型或记餐完成。收件与工具执行共用新链路的可恢复状态，不另叠加旧任务系统。
- 模型输入为：系统规则、当前可用工具、相关个人设置、最近完整对话、较早摘要、未完成事项及相关记录/提案引用。账本和知识按需通过工具获取，不把全部历史或知识库预载入 prompt。
- 未完成事项、记录引用和执行事实独立保存，不只存在摘要中。复用标准消息序列化，不实现自定义 LangGraph checkpoint 后端。
- 使用 SummarizationMiddleware；默认历史达到约 12000 tokens 时压缩，保留最近约 4000 tokens 的完整对话及工具调用/结果配对。阈值放 config.yaml；摘要保留用户限制、决定和未解决事项，不作为当前营养事实。
- 单条消息默认最多 4 次主决策模型调用、8 次工具调用，整体处理期限 90 秒；摘要仅在触发阈值时另行调用。达到上限停止追加行动，返回已完成和未完成事实。写入及依赖其结果的查询顺序执行，不额外叠加自动重试 middleware。
- 业务数字按具体工具字段、对象和时间生成；解释可由模型组织，数值片段由工具事实填入。知识回答可综合表达，但数字和结论须有本轮检索证据，保留来源。摘要、参数中的 ID 和评分不能成为数字依据。
- 已记录、已修改、已撤销和设置已生效等表述分别对应成功结果；待补全和待确认不能使用成功口径。不增加额外 LLM 审核器。

同一消息重试复用已经保存的工具调用与结果，不重新生成写入序列。写入前固定动作标识和目标，创建防重与固定 record_id 更新沿用 bitable_schema 契约；恢复时不重复已成功动作。只保留新链路所需的一套会话/执行状态，不并行维护旧计划和旧 pending 路由。

### 3.6 目标、计划与提醒

- 目标修改只更新用户指定字段，未指定字段保持原值；支持“今天有效”和“长期有效”，未指定时长期有效。模型建议的新目标经用户确认后才更新。
- 计划先读取当前目标、摄入和偏好，模型提出组合，calculate_meal 计算后才能展示营养数字。用户提出替换食物或调整份量时重新计算；明确限制无法满足时说明缺口，不编造满足结果。
- 提醒规则包含启停、餐次、HH:MM 和星期；默认关闭，时区统一使用项目配置。配置读取和修改同时支持飞书与 DSH 的自然语言入口，不新增设置页面。
- SCF 定时入口每分钟检查当前本地分钟命中的规则；仅在已启用且当日对应餐次无有效记录时发送记餐提醒。同一规则同一日期只发送一次，关闭后下一次检查即停止，不补发往日提醒。使用事实模板，不为常规提醒调用模型。
- 提醒发送至后端保存的本人最近一次飞书会话；尚无该会话时先告知用户与机器人发起会话，不启用不可投递的规则。使用现有飞书客户端，消息键由规则 ID＋本地日期固定生成，沿用回复防重机制；发送结果可查。DSH 自身的聊天回复不发送到飞书。

## 4. 执行批次与交付

依次完成下表，最后统一发布；批次间不等待重复确认。

| A：记餐业务 | 薄荷详情/单位适配、来源热量、整餐补全、历史及常用餐复用、精确定位的修改/软删除；同步 Store 两实现与数据契约。 |
| B：Agent 与管理 | create_agent、统一工具对象、多轮状态和压缩、事实回复、偏好/目标/计划；更新三预设、DSH/CLI 和相关 trace 消费者，移除被替代的旧链路及旧测试期望。 |
| C：发布 | 提醒配置与定时入口、必要验收、Linux Python 3.10 部署包、Bitable 所需表字段更新、目标 SCF 发布及真实飞书验收。 |

必要的新表字段经 storage 入口创建；保留既有业务数据。依赖更新覆盖 requirements.txt、构建脚本和部署包，保留生产 LightRAG Layer、索引及非本次修改的环境变量。主函数超时至少 120 秒。health 暴露构建标识、实际模型与检索器，不暴露密钥。

主函数发布目标固定为 ap-shanghai/default/calorie-agent-api-v3-test；飞书应用为“热量agent-v3”。保持现有 webhook 地址，不修改另外两个旧云函数。另建同地域/命名空间的 calorie-agent-reminder 定时函数，复用业务包。切换前收尾已有未完成收件；新运行时不解释旧计划协议。交付同步 REQUIREMENTS、涉及的 contracts 和 README 操作入口。

## 5. 最小必要验收

仅验收下表场景，复用 harness/eval/runner.py 和已有用例；必要时在同一入口补组合场景。只运行选定用例，不要求全量评测、先跑 smoke 基线、覆盖率目标、压测、模型横评或新增测试框架。通过后不重复运行；失败仅重跑修复影响的用例。

| 编号 | 场景与通过标准 |
|---|---|
| U01 | 明确克重和来源单位混合的整餐记录：无歧义时无额外追问；每项份量、热量及估算标记与工具数据一致。 |
| U02 | 两项信息待补全、候选选择和补数量：合并询问，保存已知信息；选定候选后接续原餐；已成功项目不重复写入。 |
| U03 | 保存常用餐→按比例复用→改单项→撤销指定项→查询：来源、日期、有效行和汇总一致；没有重新要求输入整餐。 |
| U04 | 一条消息同时记餐和知识问答，随后指代追问；强制触发一次压缩并重建 Agent：各意图均完成，引用/未完事项仍可用，历史数字不被当成本轮营养依据；只读预设不写入。 |
| U05 | 明确改目标与保存偏好直接生效；模型建议先待确认；计划计算后展示，未报告食用不产生摄入；确认只执行已展示提案。 |
| U06 | 假时钟验证提醒：关闭不发、到期未记餐发一次、重复触发不重发、已记餐跳过；常规提醒不调用模型。 |
| U07 | 同一消息重复投递，并模拟一次写入成功后处理/回复失败再恢复：不多写、不改原日期、不换动作目标，最终回复与已生效事实一致。 |

离线场景使用 FakeStore、假时钟及假模型/薄荷传输，不访问生产。既有用例与上表重复时直接复用；改变的旧业务期望同步替换，不同时保留两套行为。

发布只补以下验证：

1. 在 Linux Python 3.10 部署环境构建并启动一次，确认 Agent 和检索依赖可加载；线上 health 构建标识与发布包一致。
2. 用现有 BOOHEE_API_KEY 查询一种食物及其带 units 的详情一次；核对热量、单位和可食重。权限不足则验收个人份量回退路径，记录接口状态，不扩展供应商或套餐。
3. 一组真实飞书对话覆盖“整餐→改单项并保存常用餐→按比例复用并查询→知识问答”，核对实际 Bitable 行、工具事实和回复。凭据/权限缺失时只请求所缺配置。
4. 核对已部署的定时入口、默认关闭设置及日志可见性；提醒发送分支以 U06 验收，不额外安排线上定时等待。

验收后只软删除本次新增摄入，移除本次验收常用餐，恢复变动的个人设置。交付回复给出构建标识、必要用例结果、真实飞书/Bitable 验收结果和实际采用的份量来源；未完成项不得标为完成。
