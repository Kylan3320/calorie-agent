# 飞书＋COS 提速实施规格

状态：2026-11-02 已采用的实施与验收规格。生产迁移和切换已执行，规格验收尚未全部通过；实际构建、逐项结果及未解决项统一见 [交付记录](reports/LATENCY_DELIVERY.md)。本规格保留有效目标与判定标准，不作为后续任务自动重跑的清单。

本规格确定本轮存储、执行、迁移和验收要求。[REQUIREMENTS.md](REQUIREMENTS.md) 保存产品决定，[个人功能规格](PERSONAL_CALORIE_SPEC.md) 和 [交流体验规格](CONVERSATION_EXPERIENCE_SPEC.md) 保存业务行为。[contracts/](contracts/) 随本轮实际接口更新。

## 1. 交付目标与发布条件

用户记餐后得到可信回执，紧接着改量、补全和查询均读取刚提交的事实。飞书归档的等待不进入回复链路。

| 项目 | 执行决定 |
|---|---|
| 事实与归档 | COS 保存当前业务事实及运行状态；Bitable 保存长期业务账本和来源资料。 |
| 修改入口 | 摄入、目标、常用餐及其他个人设置通过机器人修改，Bitable 单向归档。 |
| 部署 | 上海 SCF、Python 3.10、同地域私有 COS；沿用现有飞书应用和 webhook。 |
| 模型与业务 | 现有 DeepSeek 型号及思考模式、create_agent、八工具、自然回复、营养来源和 LightRAG。 |
| 后台同步 | 每 5 分钟合并最新变更，健康链路下从业务提交到读回确认 ≤10 分钟。 |
| 本轮发布门槛 | 暖记餐、改量、今日查询各 ≤5 秒，HTTP ACK ≤3 秒；业务正确性、恢复、归档和迁移检查全部通过。 |
| 知识问答 | 内容及来源正确性必须通过。10 秒仍是速度目标，本轮单列耗时及差额，允许账本提速先上线。 |

本轮交付生产 Store、统一受理与执行、后台归档、恢复、现有入口适配、数据迁移及切换。局部实现按现有代码复用。模型或检索器替换、业务工具增删、常驻主机、外部数据库及独立消息中间件另行决定。

## 2. 数据职责

- **当前事实。** 将现有账本导入 COS 基线，后续由已提交版本更新。同一餐项只取最新版本，归档成功只推进同步水位，COS 当前事实继续保留。查询、改量和提醒均使用这一读源。
- **统计与日期。** calories、summary、items 和历史查询复用同一有效记录集合与计算口径。用户消息中的相对日期锚定原 intake_date，补全保留原餐日期，提醒使用原定时触发日期。
- **成功依据。** COS 业务提交包含实际餐项、营养依据、固定动作与结果，工具据此返回成功。收件、执行计划、提案各自保存进度。回复描述实际完成项和未完成项。
- **来源资料。** 食物库、账号映射、默认标准在迁移及维护时发布 COS 快照。薄荷补查结果先提交 COS，再后台回写食物表；已有完整资料直接复用。知识继续读取已发布 LightRAG 索引。
- **运行资料。** 收件、执行、会话、个人设置、未完事项、投递和同步进度保存 COS。消息链路中的 Bitable 访问全部移至归档或来源资料维护。

沿用现有不透明 record_id。导入餐项以原飞书行 ID 作为业务 ID，新餐项 ID 由固定 action_id 和首次确定的项序号派生。归档端另存飞书实际行 ID 的映射。

## 3. 受理、提交和恢复

### 3.1 执行归属与顺序

入口、消息处理、后台同步各部署为独立 SCF 函数，各设平台并发 1。

1. 所有 live 入口共用云端受理操作。受理记录包含消息来源、归一身份、会话、原消息键、原文、原 received_at、intake_date 及持久受理序号。重复提交复用原记录和序号。
2. 飞书收件在 COS 持久化且 SCF 异步调用被接受后返回 ACK。承接失败返回可重试错误。异步事件携带收件引用，只负责唤醒；消息端按持久序号处理同会话任务。
3. 消息处理是业务、执行与会话状态的唯一写入者。提醒定时事件及人工恢复也进入此写入者。同步端仅写自身进度，归档网络等待不占消息执行位。
4. CLI／DSH 的 live 适配器提交受理、取得持久结果并回报实际展示状态。只有飞书来源向飞书发送，提案在对应入口交付后设 presented。接口适配保留现有输出和会话隔离。
5. 每 5 分钟的后台维护先补查未完成收件并唤醒消息端，再处理归档。重复唤醒不重复业务，也不消耗已完成消息的重试次数。

### 3.2 提交边界

| 边界 | 需可靠保存的内容 |
|---|---|
| 收件 | 原消息、身份、原日期与受理序号。 |
| 模型请求前 | 预留本次调用预算，计数沿逻辑消息累计。 |
| 模型返回工具调用后 | 整批工具参数、首次顺序与固定 action_id，在任一对应动作执行前保存。 |
| 动作准备 | 固定目标及其业务版本、原日期、营养依据与绝对写入结果。 |
| 业务提交 | 本次变更、稳定 ID、完整工具结果和归档版本，构成一份可恢复提交。提交成功后才返回业务成功。 |
| 交付前 | 最终正文、UUID、会话引用及未完事项，重试复用已存正文。 |
| 交付后 | 实际交付结果和提案 presented 状态。 |

写后中断通过动作键找回原提交，跳过重复业务。没有变化的保存直接省去。会话使用现有标准序列化及摘要机制，每个保存点只处理本次相关数据。

仅摄入、食物资料或个人设置等归档内容变化时推进对应业务版本。收件、模型审计、会话或投递元数据变化不触发账本重写。

### 3.3 COS 读取与重建

各写入者使用独立状态范围、连续递增的提交编号和前驱引用，提交对象创建后不可覆盖；依赖禁止覆盖的桶关闭版本控制。提交响应不确定时保留原键，按原提交核对结果。

LIST 和可变指针用于定位候选版本。写入者开始处理任务时，通过禁止覆盖创建下一编号确认当前顺序，冲突后按确切版本追读。确认点只记录版本关系，已知版本暂不可读时转入恢复。确认当前编号后再复用该版本缓存。

按会话、目标日期／餐项及相关配置组织读取和保存。采用必要的基线与快照，当前请求不加载全部历史、不逐保存复制全库。恢复所需提交本轮保留。

shadow_fakewrite 使用 FakeStore。shadow_readonly 读取可见的已发布提交并返回版本，对 COS、Bitable、投递和 usage 零写入，包括重建确认点。live 的最新状态确认由消息写入者负责。

平台约束见 [COS 一致性](https://cloud.tencent.cn/document/product/436/30748) 和 [禁止覆盖创建](https://cloud.tencent.com/document/product/436/7749)。

### 3.4 恢复与后续消息

每次实际执行尝试自 worker 开始工作计 90 秒，最后 5 秒用于提交和交付。原 received_at 用于端到端计时，业务日期和累计模型／工具预算保持不变。

消息处理最多自动尝试 3 次，平台重试与后台补查共用持久计数。已有每消息 4 次主决策、8 次工具预算继续有效，重放已提交结果不重复占用调用预算。暂时性网络、限流、可见性和进程故障按原任务恢复，确定的配置或参数错误记录待处理。

| 恢复时的事实 | 处理方式 |
|---|---|
| 业务及回复均已完成 | 重复收件直接返回原结果，保留当前会话。 |
| 业务已提交，回复待交付 | 只补交已存回复，后续业务读取当前事实；同会话回复按顺序交付。 |
| 业务未完成，已提交部分可确认 | 恢复原固定动作。次数用尽后保存已完成部分和未完事项，交付事实回执，后续消息可继续。 |
| 某次写入结果仍未知 | 先核对原提交，保留后续相关任务；结果确定前不基于旧值继续改量或宣称写入失败。次数用尽后标记待处理。 |

人工恢复复用原任务和身份。未提交的修改只在目标仍为准备时版本时继续；目标已被后续消息修改则保留原进度，由新消息重新发起。旧任务不能回写旧会话。提醒保留原计划时间、已记餐判断和固定投递键，规则关闭时结束检查。

## 4. 飞书归档

同步端按业务版本处理摄入、食物和设置。每次选取尚未确认的最新结果，同一项尚未发出的多次改量可合并；写入采用绝对值，撤销采用软删除。

摄入表增加 agent_item_id 和 agent_revision。导入行按已知飞书行 ID 更新，新增行按 agent_item_id 定位并使用固定 client_token。食物及设置沿用已有稳定业务键。响应与餐项按稳定 ID 绑定。

一次写入的请求及目标版本在发送前保存。响应丢失先查回该次结果，确定后再推进新版本。读回确认对应字段和版本后记录同步水位，重复任务跳过已确认版本。业务提交本身即可发现待归档内容，归档工作不依赖另一次通知成功。

暂时失败保留原同步任务，下一窗口继续；确定的权限或配置错误记录待处理。同步的进度、失败和最近成功版本通过现有日志查询。COS 当前业务事实持续可用。

## 5. 实施与切换

### 5.1 接入范围

复用 Runtime、工具计算、来源适配和消息投递。presets 统一选择生产 COS Store。生产 Store 与 FakeStore 对齐业务契约，FakeStore 和验证夹具仅用于测试。COS／Feishu HTTP 均归 agent/storage/。

更新受影响的 tool_protocol、bitable_schema、trace_schema 和消费者。保留原 trace 字段，增加收件、COS 提交、投递、归档之间的关联。验证产物只复用有用的传输和故障经验，生产包按实际职责组织。

### 5.2 迁移与启用

1. 完成生产路径、候选部署及第 6 节验收，冻结通过的代码包和 BUILD_ID。候选使用独立业务命名空间，切换使用正式数据与独立生产 COS 前缀。
2. 开始短维护窗口，旧入口拒绝新受理并让调用方沿原消息键重试。排空旧执行及待发回复，等待用户补全或确认的事项随会话迁移。
3. 导入摄入含软删除标记、营养快照、来源配置、设置、会话、未完事项及已有幂等／投递状态。保留原 ID、身份、日期与数值，测试命名空间不导入。
4. 独立核对有效行数、按日合计、旧 ID 引用及去重状态，保存基线水位。启用新受理与消息处理，开启独立归档和提醒，核对实际构建、权限与触发器。
5. 通过正式入口做一条只读查询，独立核对旧账本。第 6 节发布门槛全部通过即完成接入；知识速度差额单独列入交付。

切换前可恢复旧入口。产生新 COS 业务提交后，仅回退到兼容当前 COS 提交格式的构建；首个 COS 版本故障时暂停受理并修复，保留新提交。自动反向迁移不在本轮。

沿用已有授权处理资源与配置。新增付费资源、权限扩展或不可逆数据操作集中列明具体对象和影响。

## 6. 最小验收与交付

### 6.1 离线和构建

执行一次 `python harness/eval/runner.py --case E01,E02,E03,E04,E05,E06,U05,U06`。保留独立业务预期，新存储断言进入生产 Store 和真实入口适配器，传输使用注入替身。旧接口的实现专用断言随新契约替换。

| 场景 | 必须覆盖的结果 |
|---|---|
| 连续业务 | 既有 270→210→新增 105→当天 315 成立。三种查询详情同口径；提醒看得到已提交餐项；常规已知资料请求同步 Bitable 调用为 0。 |
| 顺序与恢复 | 唤醒乱序仍按受理序号执行；提交前中断、提交响应丢失、交付后未存状态，均按原动作恢复。旧收件超过 90 秒和跨日可恢复；旧失败任务恢复不覆盖后续改量。 |
| 不确定提交 | 陈旧 LIST、已知提交暂不可见、进程重建及旧实例再次接单不产生空账本或旧值覆盖。结果未知时后续相关改量不执行；只读预设全程零写。 |
| 归档并行 | 阻塞同步传输时，消息仍能完成改量和查询。创建响应丢失、重复任务、旧版本及软删除最终保持唯一餐项和最新值。 |
| 入口与迁移 | CLI／DSH 的 live 提交及展示回报走统一通道，提案交付绑定正确。旧行、软删除、会话引用及幂等状态导入后可读，重投不复活旧记录。 |

沿用 E01–E06、U05、U06 的其他行为断言。仅在新传输边界补充缺失覆盖，修正后只复验受影响组。执行一次 Linux Python 3.10 实际包加载，覆盖各入口、COS Store、模型、LightRAG 和提醒；console、DSH、harness 和验证驱动不入云函数包。

### 6.2 候选真实链路

采用最终候选代码、真实 COS／飞书／模型／食物来源。在独立业务命名空间，以来源资料和独立底账预先确定餐项、份量及预期热量。

按顺序发 5 条新消息：初始只读查询 → 已知两项整餐 → 指定项改量 → 今日热量 → 一条带依据的知识问题。记餐至今日查询期间暂停归档，之后重投原记餐一次并恢复归档。独立解码 COS 提交及读取飞书实际行，与预先确定的预期比较。

| 项目 | 判定 |
|---|---|
| 业务质量 | 对象、日期、原餐／全天范围、数值、估算和成功状态正确；提案、未完项及知识来源遵循业务规格。质量错误阻止切换。 |
| 账本速度 | 记餐、改量、今日查询各取得一个暖样本，T_service 均 ≤5 秒。某类只有冷样本时，仅补该类一条暖样本。暖失败须修复后复验。 |
| 收件与计时 | ACK ≤3 秒，使用平台入口至 HTTP 返回或调用方测得的完整耗时。T_service 从原 received_at 至最终发送 API 成功，涵盖受理、承接、排队、保存及发送；重试不重置起点。 |
| 首次与知识 | 初始查询记录完整耗时、可取得的 T_user 及平台冷启动标记。知识记录首次加载及完整 T_service，与 10 秒目标比较；仅知识速度差额不阻止本轮切换。 |
| 归档结果 | 未归档时，改量与查询已完成。恢复归档后连同调度等待 ≤10 分钟完成独立读回，餐项唯一、版本及合计正确。 |
| 重投 | 原记餐重投不新增行、不回滚改量、不重发已交付旧回复；证据绑定本次重投及最新提交。 |

记录实际消息 ID、BUILD_ID、提交与归档版本、阶段耗时。各阶段只计一次。候选新增数据按固定 ID 清理并核对清理结果。

### 6.3 完成条件

离线、包加载、候选的质量／账本速度／ACK／归档检查、迁移核对及正式入口只读检查全部通过，完成本轮接入。失败保留原样本，只修复和复验对应步骤；无法解决的发布门槛项保持未完成。

交付更新后的接口文档、实际构建、验收结果、迁移及归档水位、清理结果和知识速度差额，统一记录于 reports/LATENCY_DELIVERY.md。
